release: v0.7.1 — install procps in agent image (fix AMD "unknown" process names)

Patch release that fixes the actual root cause of the "process_name
= unknown" issue surfaced on .210 AMD master during v0.7.0
validation. v0.7.0's resolveProcessName fallback was correct but
unnecessary in the common case: rocm-smi --showpids shells out to
`ps` to translate PIDs into process names, and the agent's runtime
image (node:22-trixie-slim) ships without `ps`. rocm-smi printed
`/bin/sh: 1: ps: not found` on stderr and returned the literal
string "unknown" for process_name, regardless of whether /host/proc
was mounted.

Adding `procps` to the agent Dockerfile fixes the issue at its
source — rocm-smi now successfully calls `ps -p <pid> -o comm=` and
returns real names. The v0.7.0 fallback in processesRocm.ts still
covers the (rarer) case where /host/proc IS mounted but `ps` isn't,
so this is belt-and-suspenders.

Diagnostic that pinpointed the cause:

  $ docker exec gpuviewr-agent-local /opt/rocm/bin/rocm-smi --showpids --json
  /bin/sh: 1: ps: not found
  {"system": {"PID1085714": "unknown, 1, 12209102848, 0, unknown"}}

The two "unknown" tokens are process_name and cu_occupancy — both
populated via `ps`-shells inside rocm-smi.

Internal
- agent/Dockerfile: procps added to the apt install line. Image
  size delta ~+250 KB.
- agent/dist/agent.mjs rebuilt at v0.7.1 (no source changes).

Known limitation still standing
- GPU% column stays `-` on AMD because rocm-smi returns
  cu_occupancy="unknown" from the driver on certain ROCm/amdgpu
  combos. Driver-side, out of scope for this release.

Upgrade
- Hub: cd ~/gpuviewr && docker compose pull && docker compose up -d
  --force-recreate
- AMD users see real process names on the next collector tick.
- The /proc bind-mount added to master docker-compose.yaml in
  v0.7.0 is still recommended for CPU% population — wget the latest
  docker-compose.yaml from main if you haven't refreshed yet.
