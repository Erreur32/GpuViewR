release: v0.7.0 — Windows AMD/Intel via PDH, AMD process-table fixes, README LLM focus

First Windows-stable release (real test green on a home RTX 3090 Ti
box earlier today). Adds AMD / Intel GPU coverage on Windows through
the same Performance Data Helper counters Task Manager uses, and
fixes three latent bugs in the AMD process collector path that
became visible the moment the .210 lab master compared its table
against the .209 NVIDIA master. README repositioned around the
project's actual design driver: monitoring local AI / LLM inference
runtimes.

Added
- AMD / Intel GPU support on Windows via PDH counters. New
  gpuWindowsPdh.ts taps Win32_PerfFormattedData_GPUPerformanceCounters
  _{GPUEngine, GPUAdapterMemory} — language-independent WMI classes,
  so French / German / non-en-US Windows installs work without the
  typical localized-counter-path hassle. One long-running powershell
  process polls the counters and emits one JSON snapshot per tick to
  stdout. Surfaces utilization (highest engine util per adapter,
  matches Task Manager) and dedicated VRAM. Temp / power / freq /
  PCIe stay null — PDH doesn't expose them; NVIDIA users keep the
  full picture via nvidia-smi.exe.
- resolveVendor's Windows fallback now routes to PDH. A Windows box
  without nvidia-smi.exe previously resolved to vendor=nvidia and
  exited at boot. v0.6.9 made it soft-fail with no GPU samples; v0.7.0
  routes it through the PDH collector so the table has real numbers.
- install.ps1 messaging updated. No longer claims "AMD on Windows is
  not supported"; describes the PDH fallback and what it covers.
- README banner names the actual AI / LLM runtimes the dashboard is
  designed to surface (Ollama, llama.cpp, vLLM, ComfyUI, Stable
  Diffusion, KoboldCpp, text-generation-webui, LM Studio).

Fixed
- AMD process table no longer renders "unknown" with empty CPU/GPU
  columns. Three independent bugs in the same path:
    1. processesRocm.ts fell back to the literal string 'unknown'
       when rocm-smi --showpids returned an empty process_name field
       (common with non-root callers and older ROCm builds). Now uses
       resolveProcessName(pid, hostProc) — argv[0] basename then
       /proc/<pid>/comm — same ladder the nvidia collector uses for
       [Not Found] / N/A rows.
    2. gpu_pct was hardcoded null. We were already parsing
       cu_occupancy (the AMD analogue of nvidia-smi pmon's SM%) and
       discarding it. Now surfaced as gpu_pct.
    3. Master docker-compose.yaml agent sidecars (both nvidia and
       amd) were missing /proc:/host/proc:ro + HOST_PROC env. The
       CPU sampler couldn't read /proc/<pid>/stat, so CPU% was
       permanently null. Added the mount on both sidecars and on
       the standalone docker-compose.agent.nvidia.yaml (the
       standalone AMD compose was already correct).

Internal
- Agent bundle: 173 KB -> 181 KB (PDH collector + minor refactor).
- agent/src/index.ts: removed the v0.6.7 win32+amd fail-fast guard.
- Three new compose changes need a full `up -d` on the hub side
  (not just `restart`) for the /proc volume to attach.

Upgrade
- Hub: cd ~/gpuviewr && docker compose pull && docker compose up -d
- Linux agents: auto-update picks up the new bundle.
- Windows agents (v0.6.7+ install.ps1): launcher.ps1 swaps in the
  new bundle on the next agent_update push.
- AMD-on-Windows / Intel-on-Windows users: re-run the install.ps1
  one-liner from the Add Host modal to validate the PDH path.
